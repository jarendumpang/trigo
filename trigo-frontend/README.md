# TriGo — HTML frontend with shared JavaScript

## Run

Copy this folder to XAMPP htdocs as trigo-frontend. Start Apache and open http://localhost/trigo-frontend/ . No npm, build process, or framework is required. The original Bootstrap 5.3.3 grid and Google Fonts links require internet access.

## Main pages

- index.html — landing page
- admin/admin.html — administrator design
- user/user.html — passenger design
- employee/employee.html — employee design

The landing, admin, user, and employee folders also contain the existing secondary HTML screens. Each page can be opened directly. Page navigation uses ordinary HTML links, not a JavaScript router.

## Files to edit

- HTML files: page layout, text, fields, tables, and sample records.
- assets/css/style.css: the supplied stylesheet, unchanged.
- assets/js/ui.js: one shared, commented file for browser interactions. There are no role-specific JavaScript files.

The supplied source's mismatched button/link closing tags were repaired. Existing layouts, colors, illustrations, and page content were retained. The current source's admin dashboard content was kept rather than replaced with an earlier version.

## Working frontend interactions

- Applicant search filters the visible HTML rows, case-insensitively.
- Daily/Weekly/Monthly/Yearly tabs update sample chart bars, labels, and nearby sample income figures.
- Dialogs open and close with Close or Escape.
- Form controls use native browser validation.
- File selection displays the selected filenames; files are not uploaded.
- Booking preview displays entered locations and the original fixed-distance fare example.
- Fare settings preview recalculates the 3.8 km example with entered rates and commission.
- Location requests are made only when the location button is pressed. Coordinates are displayed; address lookup and road routing are not implemented.
- Profile/document/support buttons show information dialogs.

The chart figures and route distance are examples. Changing text fields does not produce real road distances or a real booking. All browser interaction code uses DOM methods and textContent; pages are not generated by JavaScript.

## What belongs to PHP

No JavaScript selects or authorizes roles, logs users in, approves applications, changes ride status, changes availability, records payment, saves preferences, or stores account data. There is no localStorage or sessionStorage.

The original demo account selector remains visible to preserve the supplied login design. It has no role-routing behavior. PHP must determine the authenticated account's actual role. Likewise, cross-page preview links and the Log out link are navigation only; they do not create or destroy a session.

Buttons that require backend operations show an explanatory dialog. For example, Save does not claim that records were saved, and Go online does not claim that availability changed.

To connect your backend:

1. Rename the necessary HTML files to .php and update normal href links.
2. Add your PHP session and permission checks before output.
3. Add form action/method attributes, input names, and server validation. Comments mark the forms.
4. Remove data-frontend-form when the form should submit to PHP; the preview listener prevents form submission.
5. Replace data-backend-action on the relevant button and change its type to submit. Keep optional client validation; PHP must validate again.
6. Replace sample table rows and values with escaped PHP output. Retain data-person on applicant rows if you want the client search.
7. Replace the availability, booking, and rate-preview hooks with your real server responses as those features become available.

## How the shared script works

A data attribute in HTML identifies a small interaction. For example, data-filter enables row search, data-period identifies a chart tab, and data-message opens an informational dialog. ui.js listens for those attributes. It does not inspect the account role or select the page.

All 22 pages loaded in headless Chrome with no JavaScript errors. Local page links and CSS/script paths resolved. Browser checks exercised search and clearing, chart values/totals, dialogs, native invalid-field handling, fare calculations, safe display of typed text, file selection, and backend placeholders. Desktop and mobile screenshots were captured; the desktop booking page and mobile landing page were visually inspected.
